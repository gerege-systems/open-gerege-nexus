# Муж ба гэр — нэршлийн засвар ба хувийн орон зайн санал

**Санал.** Урсгалуудыг дахин нэрлэнэ: `tenant` → **`workspace`**,
`internal/platform` → **`operator`**, `platform` schema → **`registry`**.
Мужид хоёр төрөл гарна — **гэр** (нэг хүн) ба **байгууллага**. Иргэн
байгууллагад харьяалагдалгүйгээр нэвтэрч, өөрийн мужид ажиллана.
`EID_JIT_TENANT_SLUG` устана. Нэг байсан access унтраалга хоёр болно:
платформ хүнийг оруулах уу, байгууллага гишүүн авах уу — тусдаа асуултууд.

Иргэн нэвтэрсний дараа байгууллага руу биш, **`/me` — өөрийн гэр** рүү буух ба
100 нийлүүлэгчээс өөрөө сонгож үйлчилгээ хүсдэг болно.

Огноо: 2026-08-27 · Статус: **Үе A, B, E, G хэрэгжсэн (2026-08-27); Үе C, D, F санал** ·
Хамрах хүрээ: `backend/`, `frontend/`, `docs/`, `catalog/`

Шийдвэрийн товч нь [`adr/0006-a-person-owns-a-space.md`](adr/0006-a-person-owns-a-space.md).
Энэ баримт нь түүний **хэмжилт, хувилбар, дараалал**.

---

## 1. Юуг харсан бэ

Кодыг уншлаа. Доорх нь тоо ба байршилтайгаа.

### 1.1 `platform` гэдэг нэг үг дөрвөн зүйл хэлж байна

| Хэрэглээ | Утга | Тенантын урсгалын хамаарал |
| --- | --- | --- |
| `internal/platform/*` | Операторын урсгал | **Импорт хориотой** — `internal/planes_test.go` |
| `platform` schema | `users`, `tenants`, `apps`, quota, flags, announcements | **Заавал уншина** — нэрлэсэн 5 boundary хүснэгт |
| `pkg/platform` | Хоёр урсгалыг угсрах HTTP host package | Импортлодог |
| Прозод «платформ» | Бүтээгдэхүүн бүхэлдээ | `PlatformIsPublic()` нь `internal/workspace/auth`-д |

Эхний хоёр мөр эсрэг дүрэм үүрч байна: нэг `platform` руу хандаж болохгүй,
нөгөө `platform` руу заавал ханддаг. Архитектурын тодорхойлолт өөрөө үүнийг
тайлбарлахын тулд нэмэлт догол мөр бичих шаардлагатай болсон — *«бодит хил нь
schema USAGE биш, хүснэгтийн түвшний grant»*. Тэр өгүүлбэр хэрэгтэй болсон нь
нэршлийн зардал.

### 1.2 `tenant` бол адаптерын үг

ADR 0001: *«Домэйн бол хаана ажиллахаас үл хамааран үнэн зүйл. Адаптер бол
хаана ажиллаж байгааг мэддэг бүх зүйл.»*

`tenant` нь олон эзэмшигчтэй нэг суурилуулалт дээрх түрээслэгчийг заана —
энэ бол **байршлын** үг. Байгууллага харин хаана ажиллахаас үл хамааран
байгууллага.

Код өөрөө үнэн үгээ мэднэ. Нэг ч мөр өөрчлөхгүйгээр олдох жишээнүүд:

| Байршил | Бичигдсэн үг |
| --- | --- |
| `auth/tenants.go` | `ErrNoOrganisation`; *"Which organisation an account signs into when it does not say."* |
| `platform/tenants/tenants.go` | *"What the console may know about an organisation"*; `RegistrationNumber` |
| `db/migrations/00073` | `urtuu_reads_across_organisations` |
| `db/migrations/00076` | `the_org_chart_leaves_the_membership` |
| `frontend/app/organisation` | Байгууллагын legal profile |

**Тайлбар, миграцын нэр, ADR нь бүгд "organisation" руу нүүсэн. Зөвхөн
identifier нь `tenant` хэвээр үлдсэн.** Энэ бол нэршлийн санал биш, кодын
өөрийнх нь аль хэдийн гаргасан шийдвэрийг identifier-т буулгах ажил.

### 1.3 Хүн платформын түвшний баримт, гэвч гишүүнчлэлгүйгээр орж чадахгүй

`platform.users` глобал. `00082_users_ge_id` нь `ge_id`-д unique index тавьж
*«нэг geID = нэг хүн»* гэж бичсэн. Загвар нь хүнийг байгууллагаас
хамааралгүй гэж үзсэн байна.

Гэтэл `auth/tenants.go`:

```go
var ErrNoOrganisation = errors.New("this account does not belong to any organisation")
```

`FirstTenantFor` нь `tenant.memberships`-аас мөр олохгүй бол session нээгдэхгүй.
Схемийн зөвшөөрснийг нэвтрэлтийн код хориглож байгаа цорын ганц цэг энэ.

### 1.4 Одоогийн тойрч гарах зам нь env хувьсагч

`auth/handlers.go` дээр eID-ээр анх нэвтэрсэн иргэнийг `EID_JIT_TENANT_SLUG`
нэрлэсэн байгууллагад **гишүүн** болгож оруулна. Тэр иргэн:

- тухайн байгууллагын `CheckUserQuota`-д тоологдоно;
- түүний directory-д харагдана;
- түүний анхдагч role-ыг авна.

Кодын тайлбар өөрөө буруушаасан:

> *«provisioning somebody on their first eID sign-in is exactly the path by
> which an organisation grows without anybody choosing to add a person.»*

`accessmode.go` энэ асуултыг нэг газарт цуглуулж чадсан нь ахиц —
*«One check, at the one thing all of those paths do — create an account»* —
гэхдээ зөвхөн **бүртгэл үүсгэх эсэхийг**. Тэр бүртгэл **хаана амьдрахыг**
env хувьсагч шийдсэн хэвээр.

### 1.5 Нэг унтраалга хоёр асуулт хариулж байна

`settings.AccessMode` нь `private`/`public` хоёр утгатай. `public` гэдэг нь
өнөөдөр *«танихгүй хүн бүртгэл авна»* **ба** *(JIT slug тавьсан бол)*
*«тэр хүн миний байгууллагын гишүүн болно»* хоёуланг нэгэн зэрэг хэлж байна.

«Хаалттай систем дээр нээлттэй хэрэглэгч» гэдэг шаардлага яг энэ хоёрын
хооронд унаж байгаа юм.

## 2. Нэршлийн санал

### 2.1 Кодын нэр — олон улсын домэйний үг

| Одоо | Болох | Яагаад |
| --- | --- | --- |
| `internal/tenant`, `tenant` schema | `internal/workspace`, `workspace` schema | Hosting үгийг домэйний үгээр солино; гэр ба байгууллага хоёуланг барина |
| `internal/platform` | `internal/operator`, `operator` schema | `operator_accounts`, `operator_audit`, `gerege_nexus_operator` аль хэдийн байгаа — урсгал өөрийгөө нэрлэчихсэн |
| `platform` schema | `registry` schema | Суурилуулалтын бүртгэл: users, workspaces, apps, quota, flags |
| `pkg/platform` | `pkg/host` | Composition root, урсгал биш |
| Прозод «платформ» | «Gerege Nexus» / «суурилуулалт» | Бүтээгдэхүүний нэр урсгалын нэр байхаа болино |
| `internal/kernel` | өөрчлөгдөхгүй | Аль хэдийн зөв |

Үр дүнд `platform` дөрвөн утгаас **тэг** утга руу буурна, шинэ нэр бүр
нэг л зүйл заана.

### 2.2 Бүтээгдэхүүний толь бичиг — Монгол метафорын гэр бүл

`Гэрэгэ` ба `Өртөө` аль хэдийн нэг гэр бүл тавьсан. Түүнийг үргэлжлүүлнэ —
**гэхдээ UI, баримт, бүтээгдэхүүнд, Go пакетад биш**:

| Метафор | Юу | Байдал |
| --- | --- | --- |
| **Гэрэгэ** | Биедээ авч явах эрх — geID, нэвтрэлт | ✅ байгаа |
| **Өртөө** | Суурилуулалт хоорондын дамжлага | ✅ байгаа |
| **Гэр** | Нэг хүний өөрийн муж | 🆕 энэ санал |
| **Хот айл** | Хамтдаа буусан гэрүүд = байгууллага | 🆕 нэр, UI-д сонголтоор |
| **Тамга** | Зөвшөөрөл дардаг лац = операторын консол | 🆕 нэр |

**Метафорыг Go пакетын нэр болгохгүй.** `pkg/nexus` бол 7 хэлтэй, гадны
distribution хөгжүүлэгчид уншдаг semver гэрээ. Каир дахь module зохиогч
«хот айл» гэж юу болохыг мэдэх шаардлагагүй байх ёстой. `urtuu` энэ дүрмийг
зөрчсөн ч зөвтгөгддөг: `pkg/urtuu`-гийн тайлбар өөрөө шалтгааныг нь бичсэн —
англиар түүнийг нэрлэх үг байхгүй, «relay-post network» гэдэг тайлбар болохоос
нэр биш. «Байгууллага»-д тийм шалтаг байхгүй: `organisation`, `workspace`
хоёр долоон хэлэнд бүрэн орчуулагдана.

### 2.3 Татгалзсан нэршлийн хувилбарууд

| Хувилбар | Авах | Алдах |
| --- | --- | --- |
| Бүрэн метафор: `ger`, `khotail`, `tamga`, `nutag` | Хамгийн санахад амархан, экосистемтэй нэг өнгө | Гадны module зохиогчид хаалт; 7 хэлний орчуулгад найдваргүй; `Өргөө`/`Өртөө` нэг үсгээр ялгаатай — код болон ярианд эндүүрэл |
| `tenant` хэвээр, зөвхөн UI засах | Хамгийн хямд | `platform`-ийн дөрвөн утга үлдэнэ; хувийн муж орж ирэхэд `tenant` эцэслэн худал болно |
| `org` (`workspace`-ийн оронд) | Хамгийн богино, хамгийн үнэн — өнөөдрийн хувьд | Хувийн мужийг барихгүй: «personal org» бол өөрийгөө няцаасан нэр |
| `account` | SaaS-д танил | `platform.users`-тэй ойлголтын мөргөлдөөн |

`workspace` сонгосон шалтгаан: гэр ба байгууллага хоёуланг зөв багтаадаг
цорын ганц үг. Монголоор **«муж»** — «ажлын муж» гэдэг нэр томьёо
`SHELL_CONTRACT.md`-д аль хэдийн хэрэглэгдсэн байна.

## 3. Хувийн орон зай — гурван хувилбар

### 3.1 A — Гурав дахь plane

`internal/personal`, өөрийн origin, cookie, schema, DB role. ADR 0005-ийн
хэлбэрийг дагана.

**Татгалзсан.** `pkg/nexus`-ийн public contract-ийн **57 мөр** `tenantID`
дурддаг — `ReportEngine.Run`, `PermissionStore.GetUserPermissions`,
`Link.Enqueue`, `Directory.People`, `DocumentFiler.File`. Гурав дахь plane
гэдэг нь **тэнд ямар ч апп ажиллахгүй** гэсэн үг. Нэмээд ADR 0005-ийн гурван
үндэслэл (allowlist, олдоцгүй байдал, cookie тусгаарлалт) бүгд *операторын*
эрхээс үүдэлтэй; хувийн хэрэглэгч бол операторын эсрэг тал биш.

### 3.2 B — Хувийн муж нь муж мөр

Хүн бүрт `kind='personal'` мөр, ганц гишүүн нь өөрөө.

**Авах:** RLS, `dbguard`, module contract, app installation, permission gate —
бүгд **өөрчлөлтгүй** ажиллана. Хэрэгжүүлэлт нь нэг багана, нэг үүсгэх зам.

**Алдах:** мөрийн тоо (иргэн бүрээр), консолын жагсаалт (`tenantPageSize = 200`,
paging **байхгүй**), quota/metering-ийн утга.

### 3.3 C — Tenant-гүй session

Session нь хүн + **сонголтоор** муж. Route-ууд хүн-хамаарал ба муж-хамаарал
гэж хуваагдана.

**Авах:** хамгийн үнэн загвар — хүн бол субьект, муж бол контекст.

**Алдах:** `claims.TenantID` хоосон биш гэсэн таамгийг **бүх handler**-аас
ухаж гаргана; SDK-гийн `tenantID` хүн-хамаарлын route дээр худал болно.

### 3.4 Санал: **механизм нь B, толь бичиг нь C**

Хувийн орон зай дотооддоо муж мөр байна (B-ийн бүх ашиг), гэхдээ гадагшаа
хэзээ ч «байгууллага» гэж нэрлэгдэхгүй, байгууллагын дүрмийг үүрэхгүй (C-ийн
загвар). Тодруулбал:

**1. `kind` багана.** `registry.workspaces.kind ∈ {personal, organisation}`.
Консолын жагсаалт анхдагчаар `kind='organisation'` шүүнэ.

**2. Залхуу үүсгэлт.** Гэр нь **нэвтрэх үед биш**, хүн эхний удаа хадгалах
зүйлтэй болох үед үүснэ — гарын үсэг зурах, Өртөөгөөр даалгавар авах, апп
суулгах, баримт хүлээж авах. Эс тэгвээс eID товч дарсан бүх хүнээр хүснэгт
дүүрнэ. Идемпотент түлхүүр нь `ge_id`; түүнгүй бол бүртгэлийн `id`.
`00082`-ийн unique index энэ баталгааг аль хэдийн барьж байна.

**3. `EID_JIT_TENANT_SLUG` устана.** eID нэвтрэлт хүнийг үүсгэнэ, шаардвал
түүний гэрийг үүсгэнэ, өөр юу ч биш.

**4. Гэрт байхгүй зүйлс.** Урилга, role удирдлага, directory, хэлтсийн бүтэц,
байгууллагын квот. Гэрт нэг л дүрэм: эзэн нь бүх эрхтэй.

**5. Каталогийн `audience`.** Manifest-д `audience: personal | organisation | both`.
Үгүй бол хэлтэс, албан тушаал, батлах гинжин дээр босгосон апп хувийн мужид
утгагүйгээр урсаж орно. Анхдагч нь `organisation` — өнөөгийн бүх апп зөв
хэвээр үлдэнэ.

**6. Хоёр унтраалга.**

| Унтраалга | Асуулт | Анхдагч |
| --- | --- | --- |
| `registry.settings` → `access_mode` | Танихгүй хүн **өөрийн гэр** нээж болох уу? | `private` |
| `registry.workspaces.admission` | Хүн **энэ байгууллагад** орж болох уу? | `invite_only` |

Төрийн порталын хэлбэр яг энэ: eID-тэй хүн бүр орж **өөрийн зүйлээ** харна;
яамны ажлын мужид хэн ч урилгагүй ороогүй хэвээр.

**7. UX нь аль хэдийн бэлэн.** Мужийн сэлгүүр (`auth/session_switch_test.go`)
байгаа тул хэрэглэгчийн харах өөрчлөлт нь тэр жагсаалтад «Миний гэр» гэсэн
нэг мөр нэмэгдэх, тэгээд л боллоо.

**8. Хүсэлт гэрт амьдрахгүй.** Энэ бол саналын анхны хувилбарын **залруулга**.
Иргэний үйлчилгээний хүсэлт нь **нийлүүлэгчийн мужид** үүсч тэндээ амьдарна:
ажил тэнд хийгдэнэ, audit тэднийх, SLA тэднийх, RLS тэднийх. Гэр нь тэдгээрийг
**харах цонх** ба иргэний өөрийн эд зүйлс — geID, төхөөрөмж, буцаж ирсэн
гарын үсэгтэй баримт. Тиймээс гэр нь жижиг байгууламж; жинхэнэ ажил нь §3.5-д.

### 3.5 Эрэлтийн тал — 100 нийлүүлэгч, нэг үйлчилгээ

Хувийн орон зайн жинхэнэ шаардлага нь «иргэнд гэр хэрэгтэй» биш: **нэг ижил
үйлчилгээг 100 байгууллага санал болгоход иргэн дуртайгаа сонгодог байх.**
Энэ бол эрэлтийн тал, өөр асуудал, илүү хэцүү.

Сайн мэдээ нь: **механизм нь аль хэдийн байна.** «Өртөө» үүнийг зориудаар
зохиосон байдаг.

| Хэрэгтэй зүйл | Хаана | Юу хийж байгаа |
| --- | --- | --- |
| 100 байгууллага нэг үйлчилгээг **нэг ижил** гэж ойлгох | `urtuu_request_codes` + [`RING_STANDARD.md`](RING_STANDARD.md) (`urtuu/ring/1`) | `Д-101` хаана ч ижил утгатай — гарын үсэгтэй, хувилбартай, ETag-тай |
| Үйлчилгээ ≠ даалгавар | `00065_urtuu_two_lines` | `line='service'`: **хүсэгч заавал бий**, **хариу заавал буцна** — Go биш, `CHECK` барина |
| Хүсэгч хэн бэ | `urtuu_tasks.applicant` JSONB | Нэр, регистр, холбоо барих зам |
| «Энэ иргэний хүсэлт хаана явж байна» | `idx_urtuu_tasks_applicant` | Тэр асуулт **индекстэй** бичигдсэн байна |
| Олон байгууллагыг нэг session-д унших | `00037` / `00073` — `app.allowed_tenants` | Уншихдаа олон, бичихдээ зөвхөн идэвхтэй нэг |
| Аль байгууллага энэ кодыг нээсэн бэ | `PeerDirectory.CodeOpenOn(tenantID, peerID, code)` | Аль хэдийн хариулдаг — **гэхдээ зөвхөн холбоосын дагуу** |

`00065`-ын тайлбар шаардлагыг үг үгээр нь бичсэн байна:

> *«Иргэн эсвэл байгууллага үндсэн платформ дээр төрийн үйлчилгээ авах ХҮСЭЛТ
> гаргана… Хүсэгч тал платформын гадна байгаа тул хариуг нь хэн нэгэн буцааж
> хүргэх ёстой.»*

Ганц ялгаа: тэр өгүүлбэр **«хүсэгч платформын гадна»** гэж таамагласан. Энэ
санал түүнийг **дотогш** оруулна — тэгэхэд иргэн JSON биш, бүртгэл болно.

#### Дутуу байгаа дөрвөн зүйл

**1. Нийтийн нийлүүлэгчийн лавлах.** «Хэн `Д-101` нээсэн бэ» гэдэгт өнөөдөр
зөвхөн холбоосын дагуу хариулдаг. Иргэнд энэ нь суулгац даяарх **хайлт** байх
ёстой: код → түүнийг нээсэн байгууллагууд, нэр, харьяалал, SLA. Хэлбэр нь
консолынхтой ижил — RLS унтраасан чөлөөт query биш, дэлгэц бүрд бичигдсэн
нэрлэсэн statement. Зөвхөн нийлүүлэгч **өөрөө нийтлэхээр сонгосон** зүйл гарна.

**2. Хүсэгч бүртгэл болно.** `applicant` JSONB **хэвээр үлдэнэ** — тэр бол
нийлүүлэгчийн ажилладаг агшны хуулбар бөгөөд нийлүүлэгч иргэний бүртгэл рүү
query явуулах ёсгүй. Хажууд нь `applicant_user_id` (эсвэл `applicant_ge_id`)
багана нэмэгдэнэ. Тэр багана л «миний хүсэлтүүд» гэдгийг регистрийн мөр таарах
биш, **query** болгоно.

**3. Иргэний уншилтын зам — `allowed_tenants`-ыг өргөтгөх БИШ.** Энэ бол
хамгийн том занга. Иргэний session-д 100 байгууллагыг `allowed_tenants`-д
хийвэл тэр session тэдгээрийн **бүх** Өртөөний мөрийг уншина. Зөв зам нь мөрийн
түвшний, `applicant_user_id = me` гэсэн нэрлэсэн хэдхэн statement: иргэн
байгууллагыг уншихгүй, **зөвхөн өөрийн мөрөө** уншина.

**4. Сонголт = хүсэлт хаана үүсэхийг сонгох.** Нэг суулгац дээрх 100
байгууллагын хувьд Өртөөний **дугтуй хэрэггүй** — `target_peer_id IS NULL`,
ажил тэндээ хийгдэнэ. Өртөөний **үгсийн сан** (код, шугам, хүсэгч,
хариу-заавал) хэрэгтэй; түүний **тээвэр** нь суулгац хооронд л хэрэгтэй.

#### Урьдчилан шийдэх ёстой зүйлс

- **Жагсаалтын эрэмбэ бол бүтээгдэхүүний шийдвэр.** 100 нийлүүлэгчийн аль нь
  дээр гарах вэ? Дүрмийг зориудаар бич (цагаан толгой, харьяалал, санамсаргүй)
  — эс бөгөөс санамсаргүйгээр зар сурталчилгааны талбар бүтээнэ.
- **RING нь нэршлийг л нэгтгэнэ.** Баримт өөрөө хэлсэн: *«улс даяарх нэршлийн
  нэгдмэл байдлыг өгнө, өөр юу ч биш.»* Нэг кодтой хоёр нийлүүлэгчийн чанар
  өөр — үүнийг платформ амлахгүй.
- **`local.` кодууд лавлахад гарахгүй.** Тэдгээр нь байгууллагын дотоод орон
  зай; гаргавал нэрийн орон зайн дүрэм задарна.
- **Нэг иргэн олон нийлүүлэгч рүү нэг хүсэлт зэрэг илгээх.** Хориглох уу,
  зөвшөөрөх үү — схемийн шийдвэр, дэлгэцийнх биш.
- **Иргэн хүсэлтээ татах.** `urtuu_tasks_service_has_answer` нь хариугүй
  `COMPLETED` болохыг хориглосон. Иргэн орхивол ямар төлөв вэ — хариулт алга.
- **SLA/ачаалал харуулах нь нийлүүлэгчийн гүйцэтгэлийг ил гаргана.** Нийтлэх
  эсэх нь тэдний сонголт байх ёстой.

## 4. Иргэн хаана буух вэ — `/me`

Хувийн муж, лавлах хоёрын аль нь ч «нэвтэрсний дараа хаашаа очих вэ» гэдэгт
хариулахгүй. Тэр асуулт өөрийн гэсэн хариултай.

### 4.1 Одоогийн буулт — гурван баримт

1. **Нэвтрэлтийн анхдагч зорилго нь аль хэдийн `/profile`.**
   `frontend/app/login/page.tsx`: `useState("/profile")`. Зохиогчийн санаа
   «хүний өөрийнх нь дэлгэц» байсан.
2. **Гэтэл `/profile` рендерлэгдэхээс өмнө байгууллага сонгогдчихсон байна.**
   `FirstTenantFor` гишүүнчлэл олохгүй бол session нээгдэхгүй (§1.3), тэгээд
   `/profile` нь `Layout` дотор — түүний цэс тухайн байгууллагын суусан апп ба
   эрхээс угсрагдана.
3. **Бодит нүүр нь `/apps`.** `frontend/components/TenantChoices.tsx` үүнийг
   шууд хэлсэн: *«`/apps` is somewhere every tenant has, unlike the screen
   being stood on.»*

Иргэний хувьд `/apps` нь утгагүй нүүр: **апп суулгах бол админы үйлдэл.**

Харин `/profile`-ийн өөрийнх нь тайлбар зөв замыг зааж байна:

> *«Апп нь байгууллага тус бүрд суудаг бөгөөд админ нь устгаж чадна — хүн ямар
> таних тэмдгээр нэвтэрдгээ харах эрхийг ажил олгогч нь авч болдог байх нь
> буруу. Мөн олон байгууллагад харьяалагдах хүнд **нэг л профайл** байна,
> гишүүнчлэл тутамд нэг биш.»*

Энэ бол репо дахь цорын ганц «хүнийх, байгууллагынх биш» дэлгэц. Иргэний
нүүрийн үр нь тэр.

### 4.2 Репо дахь бэлэн ойлголт: **шугам**

`frontend/app/line/[line]/lines.ts` — шугамууд өнгөөр биш **байрлалаар**
(`posture: desk | hand | public`) ялгагдана. Kiosk шугамын тайлбар нь яг энэ
асуултын хариу: *«Иргэн өөрөө eID-ээрээ баталгаажаад үйлчилгээгээ авна.»*

Иргэн бол төхөөрөмж биш, **байрлал**. Дутуу байгаа нь иргэний шугам.

Нэг анхаарах зүйл: `line/[line]` нь өнөөдөр нэвтрэлт шаарддаггүй, native
бүрхүүлийн дотор суудаг нүүр — *«Хуудас нь нэвтрэлт шаардахгүй»* гэж өөрөө
бичсэн. Иргэний нүүр нь нэвтэрсэн, өгөгдөл харуулдаг байх ёстой. Тиймээс
`LINES`-д мөр нэмэх биш, **төрлөөрөө** шугам.

### 4.3 Маршрутын хуваарилалт

| Зам | Хэн | Одоо | Болох |
| --- | --- | --- | --- |
| `/` | Зочин | Нийтийн landing / storefront | Хэвээр — **нэвтрэлт шаардахгүй хэвээр** |
| `/apps` | Байгууллагын гишүүн | Бодит нүүр | Хэвээр |
| `/cp` | Оператор | Консол | Хэвээр |
| `/profile` | Хүн | Таних тэмдэг, төхөөрөмж, нууц үг | Хэвээр — **тохиргооны** дэлгэц |
| **`/me`** | **Иргэн** | — | 🆕 **Гэр** |

`/profile`-ыг дарж бичихгүй байх нь чухал: тэр бол «би яаж нэвтэрдэг вэ»,
нүүр биш. Гэр нь түүн рүү холбоос тавина.

### 4.4 Хаашаа явуулах дүрэм

```text
нэвтэрсэн
├── операторын origin                → /cp        (proxy.ts дээр аль хэдийн)
└── тенантын origin
    ├── гишүүнчлэлтэй                 → /apps      (хэвээр)
    ├── гишүүнчлэлгүй, зөвхөн гэртэй   → /me        🆕
    └── хоёулаа                       → сүүлд байсан нь; анх удаа → /apps
```

Сүүлийн мөр чухал: **ажилтан нэгэн зэрэг иргэн**. Ажил дээрээ нэвтэрсэн хүн
байгууллагадаа очих ёстой — гэхдээ сэлгүүрт «Миний гэр» нэг мөр болж гарна.
`TenantChoices` жагсаалтыг аль хэдийн зурдаг, «reading alongside, rather than
switching to» гэсэн `toggleActive` ч байгаа тул энэ бол **нэг мөр нэмэх** ажил.

Техникээр: `/` дээр session шалгахгүй. Оронд нь `frontend/proxy.ts` дээр 308 —
`CONTROL_PLANE_HOST` дээр `/` → `/cp` гэж хийсэн яг тэр хэв маяг
([ADR 0005](adr/0005-two-planes-one-origin-each.md) §Хэрэгжилт). Нийтийн
landing нийтийн хэвээр үлдэнэ.

### 4.5 Гэрийн бүрхүүл — өөрийн layout

`frontend/components/Layout.tsx` цэсээ суусан апп ба эрхээс угсарч, дээр нь
**хатуу бичсэн** платформын мөрүүд тавьдаг: апп дэлгүүр, харагдац, суусан
аппууд, и-мэйл баталгаажуулалт (`searchIndex`). Иргэн энэ бүрхүүлд орвол
админд зориулсан, бүх нүд нь хоосон хүрээ харна.

| Сонголт | Авах | Алдах |
| --- | --- | --- |
| (a) `Layout`-д `posture` prop | Хямд, нэг prop | Цаашид цэсний мөр бүрд «энэ хэнд харагдах вэ» гэсэн шийдвэр шаардагдана |
| (b) Гэр өөрийн layout-тай | Тодорхой хуваалт | Бага зэрэг давхардал |

**(b)-г санал болгож байна.** `frontend/app/cp/layout.tsx` бол яг энэ жишиг —
өөр үзэгчид өөр бүрхүүл; `app/kiosk` нь бүрхүүлгүйгээрээ бас жишээ. ADR 0005-ын
логик энд ч хүчинтэй: үзэгч өөр бол хуваалт нь давхардлаас хямд.

### 4.6 `HandleMe`-д юу нэмэгдэх

Өнөөдөр `/api/v1/me` нь `id`, `tenant_id`, `tenant_name`, `name`, `email`,
`is_admin`, `permissions`, `Notices`, `impersonated` буцаана. Бүрхүүл аль
хэлбэрээр зурахаа мэдэхийн тулд хоёр талбар хэрэгтэй:

- `workspace_kind` — `personal` эсвэл `organisation`. Бүрхүүл үүнээс аль
  layout болохыг шийднэ, зам таамаглахгүй.
- `ge_id` — гэрийн толгойд харагдана; иргэн өөрийн дугаараа хардаг.

`tenant_id` хоосон байж болох болох нь **гуравдугаар** өөрчлөлт бөгөөд хамгийн
болгоомжтой нь: түүнийг хоосон биш гэж таамаглаж байгаа frontend-ийн бүх цэгийг
олох ажил (§3.3-ын «C»-ийн зардал багассан хувилбар — зөвхөн нэг дэлгэцийн
хүрээнд).

### 4.7 Гэр дээр юу байх вэ

Байгаа зүйлээс угсрагдана:

1. **Үйлчилгээ авах** — код → түүнийг нээсэн байгууллагууд → сонгох (§3.5)
2. **Миний хүсэлтүүд** — `urtuu_tasks`, `line='service'`, хүсэгч нь би. Төлөв
   ба **хариу**. Энэ бол бүхэл системийн оршин байх шалтгаан
3. **Миний баримт** — надад буцаж ирсэн гарын үсэгтэй PDF
   (`00072_a_signed_pdf_is_kept`)
4. **Гэрэгэ** — geID, холбогдсон таних тэмдгүүд → `/profile`
5. **Төхөөрөмж** → `/settings/devices`

Юу **байхгүй** нь адил чухал: апп дэлгүүр, хандах эрх/үүрэг, интеграц, SSO
клиент, байгууллагын профайл. Гэр нь байхгүй зүйлээрээ тодорхойлогдоно.

### 4.8 Хийж болохгүй зүйлс

- Иргэнийг `/apps` руу буулгах — админы дэлгэц.
- Гэрийг `cp` origin дээр тавих — ADR 0005-ын cookie-гийн үндэслэл эвдэрнэ.
- `/`-ыг нэвтрэлттэй болгох — нийтийн landing нь crawler-т зориулж server дээр
  рендерлэгддэг, тэр шийдвэр зөв бөгөөд `app/page.tsx` өөрөө шалтгааныг бичсэн.
- Иргэн бүрийг ямар нэг байгууллагад role-тэй болгож «засах» — тэр бол
  одоогийн `EID_JIT_TENANT_SLUG` (§1.4), буруу хариулт.

## 5. Үе шатууд

Big-bang рефактор биш. Үе бүр дангаараа `main`-д орох чадвартай.

### Үе A — Үг тодруулах (кодын өөрчлөлт байхгүй) ✅ хэрэгжсэн

- `README.md`, `docs/*` дээр «платформ» гэдэг үгийг ялган нэрлэх:
  суурилуулалт / операторын урсгал / бүртгэлийн schema.
- `docs/TRANSLATION_GUIDE.md`-ийн толь бичигт **муж, гэр, байгууллага,
  оператор, бүртгэл** нэмэх — долоон хэлний орчуулга үүнээс эхэлнэ.
- ADR 0006 нэвтэрнэ.

**Эрсдэл:** тэг.

**Хэрэгжсэн байдал.** `TRANSLATION_GUIDE.md` §9 нь толь бичиг — долоон
хэлний орчуулга тэндээс эхэлнэ. Муж, гэр, бүртгэл гурав нь тусад нь
«захиалсан үгс» болж, Үе C хүртэл интерфэйст хэрэглэхгүй гэж тэмдэглэгдсэн:
муж бүр байгууллага байхад «ажлын муж» гэж солих нь зөвхөн бүрхэг болгоно.
Архитектурын тодорхойлолт, `CONTROL_PLANE.md`, `README.md`-д «платформын
урсгал» → «операторын урсгал» болов; бүтээгдэхүүнийг заасан «платформ»
хэвээр — интерфэйст тэр үг эхнээсээ ганц утгатай байсан.

### Үе B — `internal/platform` → `internal/operator`, `pkg/platform` → `pkg/host` ✅ хэрэгжсэн

Механик rename. Semver-т **нөлөөгүй** (`internal/`), эсвэл host package
(distribution-ууд import хийдэг — `pkg/platform` үлдээж, `pkg/host` руу
нэг мөрөөр delegate хийж, дараагийн major-т хасна).

**Баталгаа:** `pkg/platform/testdata/routes.txt` (213 мөр) **өөрчлөгдөөгүй**
байх ёстой. Өөрчлөгдвөл rename биш, зан төлөв өөрчилсөн байна.

**Эрсдэл:** бага. Ашиг: `platform` дөрвөн утгаас хоёр болж буурна, хилийг
хамгаалдаг `internal/planes_test.go` нэрээрээ уншигддаг болно.

**Хэрэгжсэн байдал.** Хоёр commit. `routes.txt` 213 мөр, sha `75e87303`
өөрчлөгдөөгүй — rename мөн, зан төлөв өөрчлөөгүй. `pkg/platform` нь
`Options` alias болон нэг мөрийн `Run` болж үлдсэн; `sso-`, `business-`,
`pos-gerege-nexus` гурвыг локал core руу `replace` хийж, `main.go`-г нь
огт өөрчлөхгүйгээр build хийж баталсан. Хасалт нь дараагийн major.

### Үе C0 — Ханыг нээх (хамгийн бага алхам)

Бүтэн ажлыг хүлээхгүйгээр «заавал нэг байгууллага руу очих» ханыг авч хаяна:

1. `FirstTenantFor` — гишүүнчлэл олдохгүй бол алдаа биш, **идэвхтэй
   байгууллагагүй** session нээнэ.
2. `frontend/proxy.ts` — нэвтэрсэн + байгууллагагүй → 308 `/me`.
3. `/me` — өөрийн layout, дотор нь `/profile`-ийн холбоос ба «Миний хүсэлтүүд»
   (одоохондоо хоосон).

**Баталгаа:** гишүүнчлэлгүй хүн нэвтэрч, `/me` дээр буудаг тест; тэр session
`/apps` дээр 403/404 авдаг тест.

Энэ үе нь C1–C4-гүйгээр ч утгатай: цаашдын бүх ажлын урьдчилсан нөхцөл нь
«байгууллагагүй session байж болно» гэдэг ганц баримт.

### Үе C1 — Гэр (B+C загвар)

1. `kind` багана + миграц; байгаа бүх мөр `organisation`.
2. Консолын жагсаалтад **paging** — `tenantPageSize = 200` таг нь энэ үеийн
   **урьдчилсан нөхцөл**, дараа нь биш.
3. `admission` багана; `access_mode`-ийн утгыг хоёр болгож салгах (§3.4.6).
4. Залхуу үүсгэлтийн зам + `ge_id` идемпотент.
5. `EID_JIT_TENANT_SLUG` устгах + `.env.example` шинэчлэх.
6. Metering: гэрийн bucket тусдаа.
7. `HandleMe`-д `workspace_kind`, `ge_id` (§4.6).

**Баталгаа:** гэр байгууллагын консолын жагсаалтад **гарахгүй** тест;
RLS-ийн тусгаарлалт хоёр гэрийн хооронд ажилладаг тест;
`ErrNoOrganisation` нь «энэ *байгууллагад*» гэсэн утгатай болж нарийссаныг
барих тест.

### Үе C2 — Хүсэгч бүртгэл болно

`urtuu_tasks.applicant_user_id` багана + индекс. `applicant` JSONB хэвээр
(§3.5.2). Нэг миграц.

**Баталгаа:** нэг иргэний хоёр өөр байгууллага дахь хүсэлт нэг query-гээр
олдоно; JSONB-гийн агшны хуулбар өөрчлөгдөхгүй.

### Үе C3 — Нийтийн нийлүүлэгчийн лавлах

Код → түүнийг нээсэн байгууллагууд. Нийтлэх нь **opt-in**; `local.` кодууд
хэзээ ч гарахгүй; эрэмбийн дүрэм зориудаар бичигдэнэ (§3.5).

Энэ бол жинхэнэ шинэ бүтээгдэхүүн — бусад үе нь дэд бүтэц.

**Баталгаа:** нийтлээгүй нийлүүлэгч лавлахад гарахгүй тест; `local.`
угтвартай код гарахгүй тест.

### Үе C4 — Иргэний уншилтын зам ба сонгож илгээх

`applicant_user_id = me` гэсэн нэрлэсэн statement-үүд. **`allowed_tenants`
өргөтгөхгүй** (§3.5.3). Дээр нь «сонгоод илгээх» урсгал.

Аюулгүй байдлын хамгийн эмзэг үе.

**Баталгаа:** иргэний session нийлүүлэгчийн бусад мөрийг уншиж чадахгүй тест —
энэ үеийн гол баталгаа, бусад нь хоёрдогч.

### Үе D — Каталогийн `audience`

Manifest талбар, анхдагч `organisation`, app store шүүлт.

### Үе E — `tenant` → `workspace` дотоод rename ✅ хэрэгжсэн

`internal/`, `frontend/`, шинэ код. SDK-д хүрэхгүй.

**Хэрэгжсэн байдал.** `internal/tenant` → `internal/workspace`, ба Go-д 450
schema-тай ишлэл `workspace.<хүснэгт>` болов. Хоёр газар schema нэрийг
шууд бичсэн байсныг зассан: `internal/operator/tenants/export.go`-ийн
`information_schema` асуулт, `internal/kernel/dbguard`-ийн RLS шалгалт.
Хөндөөгүй нь `tenant_id` багана, `tenants`/`tenant_profiles`/`tenant_quotas`
хүснэгтийн нэр, `gerege_nexus_tenant` role, `tenant_isolation` бодлогын нэр,
`app.current_tenant` GUC — тэдгээрийн эхнийх нь Үе F-ийн `pkg/nexus`-тай
хосолсон, бусад нь schema биш.

### Үе F — `pkg/nexus`: `tenantID` → `workspaceID`

**Зөвхөн дараагийн major.** `RELEASING.md`-ийн semver амлалтын дагуу.
`api.txt` snapshot байгаа нь азтай: рефакторыг механикаар шалгана — diff нь
яг 57 мөр байх ёстой.

### Үе G — Schema rename ✅ хэрэгжсэн, гэхдээ санаснаас өөрөөр

Санал нь `platform RENAME TO registry` гэж бичсэн. Бодит байдалд `platform`
нь **хуваагдсан**: 00083 нь хорин хүснэгтийг `registry`, долоог `operator`
руу нүүлгэсэн. Шугамыг таамгаар биш, тенантын role-ын grant болон кодын
ишлэлээр тогтоосон.

Тэр ялгаа нь ашгийг өөрчилсөн. Зүгээр нэрлэсэн бол *«ашиг нь хамгийн бага»*
гэсэн энэ хэсгийн үнэлгээ зөв байх байлаа. Хуваалт харин 00079 хийж чадаагүй
зүйлийг хийв: тенантын role одоо `operator` schema дээр USAGE огт авахгүй тул
хамгаалалт нэг давхраас хоёр болов.

`tenant RENAME TO workspace` нь 00084 — нэг мөр. `ALTER SCHEMA … RENAME` нь
хүснэгт, index, RLS бодлого, grant, USAGE, бүр `ALTER DEFAULT PRIVILEGES`-ийн
бичлэгийг хүртэл OID-ээрээ дагуулдгийг хоосон DB дээр туршиж баталсан.

83 хуучин миграц хуучин нэрээрээ replay хийгдэнэ: `00079` `platform` ба
`tenant`-ийг үүсгэж, `00083`/`00084` тэднийг нэрлэнэ. Шинэ DB босгоход
дараалал нь зөв.

## 6. Нээлттэй асуултууд

1. **Гэр Өртөөний peer байж чадах уу?** `00073_urtuu_reads_across_organisations`
   нь байгууллага хоорондын уншилтыг нээсэн. Иргэн даалгавар хүлээж авах нь
   энэ загварын хэдэн хувь вэ — тусдаа шийдвэр шаардана.
2. **Гэрээ устгах = муж устгах.** `deletion_scheduled_at` lifecycle байгаа нь
   сайн, гэхдээ иргэний өөрийнх нь хүсэлтээр устгах урсгал нь операторын
   устгах урсгалаас өөр (өөрийн шийдвэр, зөвшөөрөл, экспорт).
3. **Гэрээс байгууллага руу шилжих өгөгдөл.** Иргэн хувиараа гарын үсэг
   зурсан баримтаа дараа нь байгууллагадаа авчрах уу? Хариулт нь «үгүй» бол
   тэр өгүүлбэрийг хаа нэгтээ бичих ёстой.
4. **Гэрт квот хэрэгтэй юу?** Хэрэггүй гэвэл сая гэр нь storage-ийн
   төлөвлөгөөгүй өсөлт.
5. **Гэрийн тоо хэдээс хойш `registry.workspaces` хоёр хүснэгт болох вэ?**
   Хэмжилтийн шийдвэр; одоо хийхгүй, гэхдээ хэмжүүрийг нь одооноос авна.

## 7. Юуг санал болгоогүй вэ

- **Одоо байгаа хилийг сулруулахыг.** Хоёр урсгал, хоёр origin, хоёр
  identity — ADR 0005 хэвээр. Энэ санал зөвхөн тэдгээрийн **нэрийг** засна.
- **Гурав дахь plane.** §3.1-д яагаад болохгүйг бичсэн.
- **Бүх зүйлийг нэг дор нэрлэхийг.** Үе A–B хийгээд зогсох нь бүрэн хүчинтэй
  үр дүн: `platform`-ийн олон утга задарна, хувийн муж нь дараагийн шийдвэр
  хэвээр үлдэнэ.
